# Asiya AI Studio — Website

A multi-page website for Asiya AI Studio, built with Next.js 14 (App Router), TypeScript and Tailwind CSS.

## Tech stack

- Next.js 14 (App Router) + TypeScript
- Tailwind CSS (custom dark theme — see `tailwind.config.ts`)
- Google Fonts: Fraunces (display), Inter (body), IBM Plex Mono (labels/eyebrows)

## Routes

| Page | Route |
|---|---|
| Home | `/` |
| Services (overview) | `/services` |
| Service Detail (7 services) | `/services/[slug]` e.g. `/services/ai-content` |
| Pricing | `/pricing` |
| How It Works | `/how-it-works` |

| About | `/about` |

Service slugs: `ai-content`, `ai-image-generation`, `ai-video`, `social-media`, `presentations`, `ai-automation`, `seo-blog-content`.

## Running locally

You'll need [Node.js](https://nodejs.org) 18+ installed.

```bash
npm install
npm run dev
```

Then open `http://localhost:3000`.

## Editing content

Almost everything text-based lives in one file: **`lib/data.ts`**. This includes all 7 services (descriptions, packages, pricing in PKR/USD, delivery times, revisions, FAQs), process steps, site-wide FAQs, portfolio case studies, legal page text, and official contact details (`WHATSAPP_NUMBER`, `BUSINESS_EMAIL` at the top of the file). Editing an entry there updates every page that shows it automatically.

## What's ACTIVE right now

- Full multi-page site, all routes above, responsive layout
- Logo: the approved client-supplied image, used as favicon, in the navbar, footer, and About page brand showcase
- Signature "Idea → AI → Creative Result" homepage hero animation (CSS/SVG, hover-interactive per service, respects `prefers-reduced-motion`)
- WhatsApp click-to-chat (`wa.me` links with contextual pre-filled messages) and `mailto:` email links, using the official number (+92 334 2813055) and email (hk4878342@gmail.com) — defined once in `lib/data.ts` as `WHATSAPP_NUMBER` / `BUSINESS_EMAIL`
- **`app/api/project-request/route.ts`** — the real backend behind the Start Your Project form. On submit it: validates every field server-side (never trusts the browser alone), sanitizes text input, rejects obvious bot submissions (honeypot field + a best-effort in-memory rate limit), generates a request ID (`AAS-YYYY-NNNN`), and attempts both an email and a WhatsApp notification **independently** — see `lib/server/notifications.ts`. The client is told exactly what actually happened (email sent? WhatsApp sent? was anything even saved?) — never a blanket "success."
  - **Email**: sends via the [Resend](https://resend.com) REST API (plain `fetch`, no SDK dependency added) — **active as soon as `RESEND_API_KEY` is set**, inactive (and honestly reported as skipped) otherwise.
  - **WhatsApp business notification**: sends via Meta's WhatsApp Cloud API using an approved message template — **active once `WHATSAPP_ACCESS_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID`, and `WHATSAPP_TEMPLATE_NAME` are all set** (a template is required by Meta's policy for business-initiated messages; see below).
- Contact form: client-side validation and a success screen — **still does not send email anywhere yet** (only the Order form is wired to a real backend in this pass — see Known gaps)
- `app/api/webhook/route.ts`: a real Meta WhatsApp Cloud API webhook endpoint — verifies the `GET` handshake against `WHATSAPP_VERIFY_TOKEN` and safely acknowledges `POST` events with `200`, logging only non-sensitive metadata. This is for *receiving* events; sending the business notification above is a separate, one-directional call and doesn't require this webhook to be configured.
- `lib/analytics.ts` + `components/Analytics.tsx`: every meaningful interaction (page views, WhatsApp/email clicks, form submits) logs to the browser console with GA4-style event names. No personal data (name, email, phone, message content) is ever included in an event.
- `app/sitemap.ts` and `app/robots.ts`: generate a real `/sitemap.xml` and `/robots.txt` at build time from the actual route list.

## What REQUIRES EXTERNAL CONFIGURATION (not active yet)

| Feature | What's needed |
|---|---|
| Order form → real email notification | A [Resend](https://resend.com) account, `RESEND_API_KEY`, and a verified `RESEND_FROM_EMAIL` (a Resend sandbox address works for testing only) |
| Order form → real WhatsApp business notification | A Meta Developer App + WhatsApp Business Platform setup, `WHATSAPP_ACCESS_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_BUSINESS_ACCOUNT_ID`, and an **approved message template** (`WHATSAPP_TEMPLATE_NAME`) — Meta does not allow free-text business-initiated messages outside a customer's 24h session window, so a template must be created and approved in Meta Business Manager first |
| Contact form actually delivering email | Not wired yet even though the Order form now is — would reuse the same `sendBusinessEmail` helper in `lib/server/notifications.ts` |
| WhatsApp webhook receiving real traffic | Set `WHATSAPP_VERIFY_TOKEN` in your deployment env, then register the callback URL + same token in Meta App Dashboard → WhatsApp → Configuration |
| Verifying incoming webhook authenticity | `WHATSAPP_APP_SECRET` + implementing the `X-Hub-Signature-256` check (stubbed but not wired in `app/api/webhook/route.ts`) |
| Google Analytics 4 | Set `NEXT_PUBLIC_GA_MEASUREMENT_ID` — the script loads automatically once it's present, and stays off otherwise |
| **Persistent order storage** | A database (`DATABASE_URL`) — **currently there is none.** If a project request comes in and both the email and WhatsApp notification fail, that request is not saved anywhere; the API honestly returns an error telling the client to contact the business directly rather than pretending it was captured |
| Reliable rate limiting | The current limiter (`lib/server/notifications.ts`) is in-memory per serverless instance — real protection at scale needs a shared store (e.g. Upstash Ratelimit) or your host's built-in abuse protection |
| Payments (EasyPaisa, Payoneer, cards, bank transfer) | A specific provider chosen + integrated; order confirmation currently states "payment details will be provided after project confirmation" and nothing more |
| Conditional order-form fields per service | Data/config for this already exists in `lib/data.ts` (`conditionalFieldsConfig`) but `components/OrderForm.tsx` does not yet render them — the form fields are still the original simpler set |

None of the above is faked in the UI — where a feature isn't connected, the interface (and the API's JSON response) says so explicitly.

## Deployment

**Vercel (recommended):**
1. Push this project to a GitHub repository
2. Go to [vercel.com](https://vercel.com), import the repository
3. Add any environment variables you're using (see `.env.example`) in Project Settings
4. Vercel auto-detects Next.js — click Deploy

**Netlify:** push to GitHub, import the repo, build command `npm run build`, publish directory `.next` (use the official Next.js Netlify plugin).

**Before going live:** update `BASE_URL` in `app/sitemap.ts` and `app/robots.ts`, and `metadataBase` in `app/layout.tsx`, to your real production domain.

## Environment variables

See `.env.example` for the full list with explanations. None are required for the site to run locally — they only unlock the "requires external configuration" features above.

## Known gaps (intentionally not built yet)

- Order form doesn't render the conditional per-service fields yet (data/config ready in `lib/data.ts`, form not updated)
- Contact form is not wired to `sendBusinessEmail` yet — only the Order form is, in this pass
- No persistent database — a submitted request that fails both email and WhatsApp notification is not saved anywhere; the API is honest about this rather than pretending otherwise
- No file upload on the order form
- No client dashboard, admin panel, or blog/CMS
- Portfolio items are clearly labeled sample projects, not real client work
